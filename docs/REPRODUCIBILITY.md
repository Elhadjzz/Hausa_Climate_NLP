# Reproducibility

## Canonical data representation

The GitHub release stores HESTC-10K as **24 part-level CSV files** under:

`data/corpus_parts/`

This design makes each corpus part independently inspectable, keeps Git diffs manageable and avoids treating a monolithic binary workbook as the canonical research object.

The exact expected count of every part is recorded in:

`data/corpus_parts/MANIFEST.csv`

## Reconstruct the 11,034-row master corpus

From the repository root:

```bash
python src/merge_corpus_parts.py
```

The script reconstructs:

- `data/HESTC10K_master.csv`
- `data/HESTC10K_review_priority.csv`
- `data/HESTC10K_merge_QA.json`

The merger verifies:

- every expected part is present;
- every part has its expected record count;
- total records = 11,034;
- IDs are unique;
- preferred English labels are unique case-insensitively;
- concise definitions are populated;
- source institutions and URLs are populated;
- source URLs are HTTP/HTTPS links; and
- Hausa candidate fields are populated.

## Run the independent QA script

After building the master file:

```bash
python src/qa_corpus.py data/HESTC10K_master.csv --json-out build/qa.json
```

## Run regression tests

```bash
pip install -r requirements.txt
pytest -q
```

The tests can read the part files directly even if the generated master CSV does not exist.

## Source registry

The authoritative resource registry is:

`data/HESTC10K_source_catalogue.csv`

It contains 243 source-resource records and preserves institutional attribution, resource title, scope used in HESTC, URL and curation note.

## Rebuild from earlier curated staging data

`src/build_hestc10k.py` documents the original corpus assembly architecture. It expects:

- an authoritative source registry;
- curated English staging CSVs;
- optional Hausa candidate records keyed by stable HESTC ID.

Example:

```bash
python src/build_hestc10k.py \
  --sources data/HESTC10K_source_catalogue.csv \
  --raw-dir staging/ \
  --hausa-candidates staging/hausa_candidates.csv \
  --out-dir build/
```

The staging records are conceptual curation inputs; they are not regenerated by scraping.

## Candidate terminology

`src/hausa_candidate_engine.py` documents the conservative rule-based component used during provisional terminology drafting. It uses known equivalents, compositional patterns, hybrid terminology and explicit expert-coinage fallback.

It does **not** validate terminology.

## Climate-NLP example

After generating the master file:

```bash
python examples/climate_terminology_grounding.py \
  --corpus data/HESTC10K_master.csv \
  --text "Climate adaptation and early warning systems reduce disaster risk."
```

## Original development resources

The project workflow used:

- Python for structured corpus processing and QA;
- regular expressions for normalization;
- CSV/JSON for machine-readable interchange;
- dictionaries and counters for deduplication/QA;
- structured spreadsheet tooling for workbook construction and inspection;
- official institutional webpages and technical resources for English-source curation; and
- large-language-model assistance for **provisional** Hausa candidate drafting.

## Important methodological boundary

The repository reproduces the corpus assembly and validation-control logic. It does not pretend that expert concept selection, source interpretation or Hausa terminology approval can be replaced by an automatic scraper or a single translation script.

Human linguistic and scientific review remains necessary before any entry is promoted from `Candidate drafted` to `Validated`.
